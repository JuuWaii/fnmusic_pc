# WinUI 3 原生客户端迁移大纲

日期：2026-09-11。本文件为阶段 0 的规划基线；后续进展见 [迁移进度](PHASE_STATUS.md)，阶段 1 接口证据见 [NAS 接口契约](api/NAS_API_CONTRACT.md)。

本阶段不实施完整重构、不删除旧客户端、不安装开发工具、不打包发布。需求来源为本机 `Project Introduction.txt`；该文件包含个人连接信息，已加入忽略规则，不应提交。本文不记录真实服务器地址、账号、Cookie、令牌或原始响应。

## 一、需求与边界

目标是以 C#、WinUI 3 和 XAML 实现完整 Windows 本地客户端：欢迎页、设置、曲库、搜索、播放页、队列等均由原生界面呈现，播放器直接使用服务端接口，不再依赖音乐网页嵌入和 DOM 注入。

“本地客户端”指界面与播放控制在本机运行，音乐仍可从 NAS 在线读取；离线下载和 NAS 服务端改造不纳入基本范围。

必须保留或实现：首次连接配置及设置中修改地址、登录状态持久化、FN Connect 远程访问、应用内音频输出设备选择、完整基础播放能力、Git 版本管理、开源依赖归属说明与多轮审查。桌面歌词在基础能力完成后作为可选阶段。GitHub 发布须另获用户明确授权。

## 二、现状与探查结论

### 仓库

- 当前版本为 Electron 0.1.18，核心结构包括主进程、网页侧脚本、本地 HTML 设置面板及测试。音频设备和播放控制仍与网页交互耦合，无法通过替换窗口框架直接迁移。
- 工作区已有大量暂存的目录重构及功能修改，尚未形成完成验收的提交。本轮保留这些修改，不将它们误认作干净的发布基线。
- 已有睡眠定时、快捷键、置顶等桌面功能代码，迁移前应逐项确认实际行为，尤其定时结束是静音还是暂停。
- 当前 JavaScript 测试通过：65 项 headless 检查与 10 项 Node 测试。它们只能证明现有检查范围，不能证明新客户端或真实 NAS 全链路可用。
- 尚无 C# 解决方案。环境能找到 dotnet 主程序，但未列出 SDK；常见 .NET SDK 与 Windows SDK 目录未发现，原生构建工具链仍需确认和配置。
- 设置界面乱码尚未完成运行时定位。检查的设置源码为有效 UTF-8，未发现替换字符，这不能排除运行时编码或字体问题。新界面必须验收中文资源、输入及文件名显示。

### NAS 页面与接口

对用户指定的音乐页面进行了只读静态探查：页面返回 HTTP 200，声明 UTF-8，标题为飞牛音乐。公开前端脚本中发现以下候选路径：

| 路径 | 静态代码中的线索 | 验证状态 |
| --- | --- | --- |
| `/api/stream/unified` | 使用 `fileId`、`quality`；调用代码读取 JSON 中的 `playlistUrl` | 静态发现，未进行鉴权回放 |
| `/api/stream/info` | 调用代码使用 `fileId` 或 `url` 参数 | 静态发现，响应契约未知 |
| `/api/stream/hls` | 流播放相关路径 | 静态发现，方法及参数待确认 |
| `/api/stream` | 流播放相关路径 | 静态发现，方法及参数待确认 |

上述内容不是已验证的完整 API 文档。登录、续期、退出、曲库、搜索、歌单、收藏、封面和歌词接口仍待确认。没有提交账号密码，没有读取用户歌曲列表，没有执行写操作。原始静态页面和脚本只保存于已忽略的 `.review-audit/`，不纳入源代码或发布物。

FN Connect 官方资料描述了 FN ID、远程访问和证书等使用方式，但不能据此认定存在可直接使用的第三方原生客户端 SDK。先验证用户配置的官方远程入口及其认证和重定向行为；不预先承诺自行实现其 P2P 协议。

## 三、目标架构

采用 WinUI 3 + XAML + MVVM。实施启动时选定受支持的 .NET 版本及 Windows App SDK Stable 版本，锁定依赖，不在本阶段盲目指定版本号。

建议在 `native/` 中独立建设，先与旧客户端并存：

```text
native/
  FnMusic.sln
  src/
    FnMusic.App/              # XAML、ViewModel、导航、中文资源、组合入口
    FnMusic.Core/             # 领域模型、业务规则、服务接口
    FnMusic.Infrastructure/   # NAS API、认证、连接配置、本地存储
    FnMusic.Windows/          # 原生播放、音频设备、系统媒体控制、桌面集成
  tests/                     # 核心逻辑、契约、集成及必要 UI 测试
docs/api/                    # 脱敏契约和合成样例
```

依赖方向：App 负责组装；Infrastructure 与 Windows 实现 Core 中的接口；Core 不依赖 UI 或服务器传输细节。无需为了分层再拆分大量小项目。

2026-09-12 按用户要求调整：由 FFmpeg 负责音频解码，Windows 媒体管线接收 PCM 并负责设备输出、时钟和系统媒体控制。真实音频格式、鉴权请求头、重定向、Range、HLS 和跳转进度仍须实测。FFmpeg 版本、构建选项及分发许可证单独审核；当前实现与限制见 [FFmpeg 播放层](FFMPEG_PLAYBACK.md)。

认证信息按连接目标隔离，使用 Windows 提供的加密存储能力，失败时不得回退为明文。不得将凭据转发到任意重定向目标，不得按整个域名后缀放宽信任，不关闭 TLS 校验。普通设置与敏感凭据分开保存。

## 四、分阶段执行与验收关卡

| 阶段 | 工作范围 | 交付与通过条件 |
| --- | --- | --- |
| 0：分析与大纲（本轮） | 需求、仓库、静态接口线索、风险、路线 | 本文；私人需求文件排除提交；保留现有工作区 |
| 1：接口契约与可行性 | 登录/续期/退出、曲库分页、搜索、封面、歌单/收藏、音频流；核对远程入口 | 脱敏接口清单，标明“静态发现/实际验证/未知”；确定鉴权与播放链路，列出服务端版本约束 |
| 2：原生工程骨架 | 工具链、解决方案、依赖注入、导航、欢迎页、设置、中文资源、日志边界 | 本机可构建启动；中文及主题正常；连接参数可编辑；演示数据必须明确标识 |
| 3：最小完整播放链路 | 原生登录、重启免登录、歌曲列表、真实音频、暂停/进度/音量、输出设备 | 在真实 NAS 上登录并播放一首歌曲；重启恢复会话；可拖动进度和切换设备；到期与错误有明确处理 |
| 4：完整音乐功能 | 搜索、专辑/歌手、详情、播放队列、随机/循环、收藏、歌单 | 按旧应用功能表逐项验收；分页、空态、失败重试及用户主动写操作正确；不以占位数据冒充完成 |
| 5：远程与桌面体验 | FN Connect 实际远程访问、断线恢复、托盘、快捷键、置顶、睡眠定时、媒体键、设备热插拔 | 内网与真实外网分别验证；切换服务器不串会话；定时行为明确；恢复播放不重复创建播放器 |
| 6：可选桌面歌词 | 已验证歌词来源、时间同步、桌面歌词窗口和开关 | 有歌词、无歌词、拖动进度、曲目切换均正确；缺少可靠接口时记录限制，不阻塞基础版本 |
| 7：替换、清理与发布准备 | 迁移非敏感设置、移除被替代代码、许可证、安装升级、隐私及多轮审查 | 功能对照表通过后才清理 Electron；生成经验证的安装包和脱敏说明；获得用户授权后发布 |

阶段 1 先做只读验证。需要登录态才能验证的内容，应通过用户正常登录建立受控测试会话，不扫描其他主机或提取无关应用凭据。歌单/收藏等写入操作不能为了探测而随意修改真实数据。

**关键关卡：阶段 3 必须证明原生登录、会话持久化与真实播放可行，才能大规模展开完整页面。** 若遇到服务端不支持、格式不兼容或认证限制，应记录具体证据和可选方案，不能用网页嵌入悄悄替代原生目标。

## 五、迁移和清理原则

1. 先盘点当前暂存内容与现有功能，形成可回退基线，再开始新的原生实现。不要自动丢弃或覆盖用户修改。
2. 新客户端使用自己的数据目录。仅按白名单迁移普通设置；不直接复制 Chromium Cookie 数据库。首次迁移可重新登录一次，之后应满足会话持久化要求。
3. 功能验收通过前保留旧客户端。通过后再清理 Electron 依赖、注入脚本、HTML 面板、旧构建脚本和过时文档，检查图标、许可证、工作流等实际引用。
4. 打包形式在工具链阶段确定，比较 MSIX 的签名和安装要求与其他原生安装方式。先验证 Windows x64；其他架构另行验证，不宣称未测试的平台可用。
5. 不擅自改写 Git 历史。若发现历史秘密，先处理凭据失效及当前暴露，再单独确定历史清理范围。

## 六、隐私与多轮审查

隐私检查贯穿每阶段，不等最后一次集中处理。服务器连接信息可以在用户本机受控保存，但不能进入仓库、截图、遥测、发布日志或安装包。通用 API 路径可以记录，个人 API 密钥、令牌和原始响应不能发布。

- 第一轮：功能与接口。核对登录持久化、会话失效、歌曲/搜索/队列、播放跳转、取消与并发、音频设备、远程连接及错误恢复；结合合成契约测试与真实 NAS 验证。
- 第二轮：架构与隐私。检查依赖方向、资源释放、事件取消、凭据加密、来源隔离、TLS、日志脱敏、缓存退出清理；扩展隐私扫描至 C#、XAML、资源、配置、测试样例及构建物。对发现的问题修复并复测。
- 第三轮：发布与回归。在干净 Windows 用户环境验证安装、升级、卸载、首次配置、中文显示、常见音频格式、待机唤醒及实际发布包内容；复核开源许可证和第三方声明。

不同轮次使用不同检查清单与证据，不能把重复运行同一个测试称为完成多轮审查。自动扫描不能单独证明隐私已全部移除，仍须人工检查发布范围和产物。参考开源实现时保留所需归属；不将 NAS 前端脚本整体复制进新应用。

## 七、额度与交接方式

每次只推进一个有明确验收点的子任务；阶段较大时拆为多轮，不一次完成整张路线表。阶段结束记录修改文件、验证命令与结果、未解决风险及下一步。可复用忽略目录内的探查缓存，但只将脱敏结论写入文档，避免反复抓取或输出大型脚本。

下一轮建议从阶段 1 的“认证与一首歌曲的播放接口契约”开始。当前仍待确认：登录协议、Cookie/令牌生命周期、流的认证方式、实际音频格式，以及 FN Connect 在外网的链路行为。此时不需要先完成整套 UI。
